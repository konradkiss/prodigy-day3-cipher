One run of the review prompt (in README.md) in a fresh `claude -p` session, Claude Code 2.1.312, on 28 October 2026. The folder held only src/ with the code comments removed. Tools: Read, Glob, Grep, WebSearch, WebFetch. 93 s, 12 turns.

---

I found five problems in `src/NaiveCipher.cs`. An attacker can read messages, change them and replay them. They can also get the key if it is a human-chosen password. I haven't written or run any of the tests below; each one describes how to prove its finding. I also didn't see the code that calls this class, so where a finding depends on that code, I say what it needs.

### 1. Read any message without the key (padding oracle): line 25, with no integrity check anywhere
- **Code:** `DecryptCbc` uses CBC with .NET's default PKCS#7 padding, and nothing checks a MAC first. `Encoding.UTF8.GetString` never throws, so the only exception `Decrypt` raises is the one for bad padding.
- **What the attacker can do:** this only needs the attacker to be able to send ciphertexts to `Decrypt` and see whether it failed, either from the error or from timing. They can then recover the plaintext one byte at a time. The IV is a fixed, public zero block, so the first block is also exposed: the attacker sends `X || C1`, choosing `X` themselves.
- **Test:** `oracle(c) = try { Decrypt(c); return true; } catch (CryptographicException) { return false; }`. Run a standard padding-oracle attack that uses only `oracle` against `Encrypt("<secret>")`, then assert that the recovered text equals `<secret>`.
- **Source:** Microsoft Learn, [CBC decryption vulnerability](https://learn.microsoft.com/en-us/dotnet/standard/security/vulnerabilities-cbc-mode). It describes vulnerable code as code that "Decrypts data using the CBC cipher mode with a verifiable padding mode, such as PKCS#7 … without having performed a data integrity check". It says the attack needs "no more than 4096 attempts per block".

### 2. Change a message without being noticed: lines 18 and 25
- **Code:** there is no MAC and no authenticated mode such as AES-GCM.
- **What the attacker can do:** flipping bits in ciphertext block *j* flips exactly the same bits in plaintext block *j+1*. `Decrypt` returns the changed string with no error. Block *j* comes out garbled, but `GetString` just turns the garbage into replacement characters.
- **Test:** encrypt `"0123456789ABCDEFamount=0000100;;"`. XOR byte 7 of the ciphertext (block 1) with `'0' ^ '9'`. Assert that `Decrypt` returns a string containing `amount=9000100` and does not throw.
- **Sources:**
  - NIST SP 800-38A, Appendix D, Table D.2. For CBC, a bit error in Cⱼ causes a "specific bit error" in the decryption of Cⱼ₊₁.
  - OWASP [Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html): for CBC, "separate authentication should be implemented".
  - The Microsoft Learn page above, which requires encrypt-then-MAC.

### 3. Get the key, if it is a password: line 12
- **Code:** the key is one SHA-256 hash of a string, with no salt, no work factor, and no check on its length or strength. `new CipherOptions("")` is accepted.
- **What the attacker can do:** with a single captured ciphertext, they can guess passwords offline at fast-hash speed. A guess is right when decryption produces valid padding and readable UTF-8. If the key string is already 256 random bits, this is not exploitable. Nothing in the code enforces that.
- **Test:** encrypt with `new CipherOptions("summer2024")`. With no other access, loop over a common-password list, call `DecryptCbc` with each candidate, and assert that the correct key is found.
- **Sources:**
  - Microsoft Learn (same page, sample remarks): the key "should be a 128-bit (or bigger) value generated by a secure random number generator". A passphrase "should be properly turned into keying material via a Key Derivation Function like PBKDF2".
  - OWASP Cryptographic Storage Cheat Sheet: "Keys should be randomly generated using a cryptographically secure function", or derived from a passphrase with a KDF.

### 4. Messages leak through matching ciphertexts (fixed zero IV): line 10, used on lines 18 and 25
- **Code:** encryption is deterministic. The same message always gives the same ciphertext. Messages that share leading 16-byte blocks share the same leading ciphertext blocks.
- **What the attacker can do:** they can tell when two messages are equal or start the same way. If they can get guesses encrypted, they can confirm a guess by comparing ciphertexts.
- **Test:**
  - `Assert.Equal(Encrypt("yes"), Encrypt("yes"))`
  - The first 16 bytes of `Encrypt("AAAAAAAAAAAAAAAA-x")` and `Encrypt("AAAAAAAAAAAAAAAA-y")` are equal.
- **Sources:**
  - NIST SP 800-38A §6.2: the CBC IV "need not be secret, but it must be unpredictable" (Appendix C covers how to generate one).
  - Microsoft Learn (page above): CBC's IV exists so that "encrypting the same message with the same key doesn't always produce the same encrypted output".

### 5. Replay: lines 21–26
- **Code:** `Decrypt` has no state and no message ID, counter or timestamp.
- **What the attacker can do:** a captured ciphertext decrypts successfully for as long as the key stays the same. Because of finding 4, the receiver can't even tell a replay from a new message with the same content. Replay protection could live in the protocol around this class, but I didn't see that code, and the class itself offers none.
- **Test:** `c = Encrypt("transfer 100 to bob")`. Assert that `Decrypt(c)` succeeds twice and returns the same text both times, with nothing recording that the first one was used.
- **Source:** OWASP Cryptographic Storage Cheat Sheet: "If an attacker could resend a ciphertext, add your own replay check, such as a unique message ID the recipient tracks."
